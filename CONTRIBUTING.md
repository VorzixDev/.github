# Contributing to VorzixDev Projects

Thank you for your interest in contributing to VorzixDev.

## 1. Before Contributing

Before starting work:

1. Confirm that the repository accepts external contributions.
2. Review the repository README, licence, security policy, and issue tracker.
3. Discuss substantial changes before implementing them.
4. Do not begin confidential or commercial project work without the required written project terms and access approval.

An unsolicited contribution may be reviewed, modified, declined, or closed. Submission or acceptance of a contribution does not automatically create employment, compensation, revenue-share, ownership, or continuing-maintenance rights.

## 2. Types of Contributions

Depending on the repository, contributions may include:

- Code and scripts
- Documentation
- Tests and bug reports
- UI/UX proposals
- 2D or 3D assets
- Animation, VFX, or audio
- Build and workflow improvements
- Security fixes submitted through the approved private process

Repository-specific rules take priority over this default guide.

## 3. Originality, Licensing, and Provenance

Contributors must:

- Submit only work they created or are authorized to use.
- Identify third-party code, assets, fonts, audio, models, textures, plugins, libraries, datasets, and templates.
- Preserve required notices and attribution.
- Disclose licence conditions that may affect commercial distribution, modification, sublicensing, or redistribution.
- Disclose material AI assistance when it affects provenance, licensing, security, accuracy, or review.
- Never copy assets or code from games, applications, repositories, media, or marketplaces without permission.

VorzixDev may request original source files, project files, dependency information, licences, or creation evidence.

## 4. Development Workflow

Unless a repository says otherwise:

1. Create or reference an approved issue.
2. Work in a separate branch.
3. Keep each pull request focused on one purpose.
4. Use clear commit messages.
5. Add or update tests and documentation where appropriate.
6. Complete the pull-request checklist.
7. Address review comments before requesting final approval.

Do not commit secrets, credentials, tokens, private customer data, payment data, or confidential agreements.

## 5. Code Quality

Code contributions should:

- Be readable, modular, and appropriately documented.
- Validate untrusted input.
- Avoid unnecessary loops, connections, memory leaks, and duplicated logic.
- Prefer configuration over hard-coded project values where appropriate.
- Include error handling and safe defaults.
- Avoid hidden network requests, telemetry, external loaders, or obfuscated logic.
- Respect client-server boundaries and repository security requirements.

For Luau and Roblox work, server-authoritative validation is expected for security-sensitive actions. Repository-specific architecture and naming rules apply.

## 6. Asset and Media Quality

Non-code deliverables should include, where applicable:

- Editable source files
- Exported production files
- Clear naming and folder structure
- Scale, pivot, hierarchy, and performance information
- Licence and source records
- Technical requirements for integration
- Preview files and reasonable revisions

## 7. Tests and Evidence

A contribution may require:

- Reproduction steps
- Expected and actual results
- Device, platform, engine, and version information
- Screenshots or video
- Logs and error output with sensitive information removed
- Test cases and retest results

Only work recorded as accepted through the applicable review process is treated as an accepted project contribution.

## 8. Review and Acceptance

VorzixDev may mark a submission as:

- Accepted
- Accepted with follow-up work
- Pending revision
- Declined
- Out of scope

Approval of a pull request confirms repository acceptance of that change. It does not by itself modify a separate contributor's compensation, revenue-share, intellectual-property, or maintenance terms.

## 9. Security Reports

Do not open a public issue for a vulnerability, leaked secret, exploit, or access-control problem. Follow [SECURITY.md](SECURITY.md).

## 10. Questions

For contribution questions, contact **vorzixdev.official@gmail.com** or use an approved VorzixDev project channel.
