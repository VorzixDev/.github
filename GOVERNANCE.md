# VorzixDev Project Governance

## Purpose

This document explains the public operational structure used to manage VorzixDev repositories and projects. It does not publish private commercial terms, contributor percentages, personal records, or confidential agreements.

## Roles

- **Organization Owner:** Controls organization security, membership, repository ownership, sensitive settings, and final access decisions.
- **Project Lead:** Defines approved scope, milestones, task assignments, review process, integration plan, and release readiness.
- **Maintainer or Reviewer:** Reviews issues, pull requests, assets, tests, and documentation within assigned permissions.
- **Contributor:** Performs approved work within a defined scope and separately accepted terms.
- **Volunteer QA Tester:** Participates voluntarily in approved unpaid testing assignments unless a separate written agreement states otherwise.
- **Community Moderator:** Manages conduct in assigned spaces without automatic repository, financial, code, or customer-data access.
- **Administrator:** Receives only specifically approved permissions under least-privilege review.

## Operational Authority

- Task assignment and scope changes require approval from the assigned Project Lead or Organization Owner.
- Pull requests require review by an authorized maintainer for the relevant repository.
- Commercial release approval belongs to the assigned Project Lead and, where required, the Organization Owner.
- Repository access changes belong to authorized organization management.
- Compensation and revenue-share changes require separate written acceptance by affected parties.

## Access Control

Access is limited to the repositories and permissions required for assigned work. Organization-owner access is restricted. Accounts and credentials must not be shared. Access may be reviewed, reduced, or removed when responsibilities change.

## Contribution Acceptance

Work is not accepted merely because it was started, uploaded, committed, or demonstrated. Acceptance requires the applicable scope, submission method, review, and recorded decision.

## Compensation Classification

A project-specific agreement should classify a role as fixed fee, revenue share, hybrid, reward-based, or voluntary unpaid participation. Public GitHub activity does not by itself create compensation rights.

## Conflicts and Appeals

Project concerns should first be raised privately with the assigned Project Lead. Security concerns follow [SECURITY.md](SECURITY.md). Conduct concerns follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

A documented appeal may be escalated to the Organization Owner or, where practical, another authorized reviewer who was not the original decision-maker.
